# keel

Інструмент методики Keel. Він знає стан і не пише прози.

Методика — те, що має бути правдою — лежить у [METHODOLOGY.md](METHODOLOGY.md),
главами й параграфами, і цитується як `§4.2`. Тут — чим це запускається.

## Що це вирішує

Агент пише швидко й переконливо, і саме тому за ним важко встежити. Він каже
«зробив», а зробив інше; додає файл, якого ніхто не планував; пише тест, який
зелений і нічого не доводить. Кожна з цих поломок тиха: усе виглядає добре.

Keel робить дві речі. **Передбачувано** — домовлене наперед записане так, що з
нього виводиться робота: сценарій стає тестом, трансформа стає коммітом, список
файлів стає межею. **Простежувано** — стан ніде не пишеться руками, він
рахується з git і з документів, тож збрехати ним не можна.

Сутностей дві: **хвиля** — те, що робимо зараз, і **контракт** — обіцянка, яка
переживе хвилю. Усе інше виводиться.

## Як це виглядає

Одна хвиля — один файл. Шапка англійською, бо її поля стають кодом; проза мовою
проєкту, бо її читає людина.

`keel/waves/0007-session-loop.md`

```markdown
---
depends_on: [0005-flat-tools, 0006-graph-tools]

scenarios:
  finishes-when-no-tool-called:   {proves: session-run@7c40de}
  only-handed-tools-are-callable: {proves: session-run@7c40de}

transforms:
  drive-turns-on-reqllm:
    implements: [finishes-when-no-tool-called, only-handed-tools-are-callable]
    contracts:  [session-run@7c40de]
    files:
      - lib/keel_agent/session.ex
      - test/keel_agent/session_test.exs
---

## Навіщо

Одна розмова з моделлю проти набору інструментів, який дали ззовні.

## scenario: finishes-when-no-tool-called

**Given** початковий контекст і порожній набір інструментів,
**When** модель відповідає текстом без виклику,
**Then** розмова завершується станом `:finished`, а в записі є хід.

## transform: drive-turns-on-reqllm

Крутити ходи, доки модель кличе інструменти.

Межі: лічильника спроб немає — відмова інструмента це відповідь,
і наступний хід є повтором.
```

Контракт лежить окремо, бо живе довше за хвилю, яка його створила:

```markdown
---
module: KeelAgent.Session
exports:
  - "run(Context.t(), [Tool.t()], Config.t()) :: Outcome.t()"
---

Одна розмова з однією моделлю.
```

А тест показує, який саме сценарій він доводить — і в якій редакції:

```elixir
@tag proves: :finishes_when_no_tool_called, rev: "a3f1c0"
test "розмова завершується, коли модель не кличе інструментів" do
  outcome = Session.run(opening(), [], config())

  assert outcome.stop == :finished
end
```

Три хеші в цьому прикладі — не прикраса. `session-run@7c40de` каже, **яку
редакцію** обіцянки реалізує трансформа, а `rev: "a3f1c0"` — яку редакцію
сценарію доводить тест. Перепишіть текст — і перевірка скаже, що доказ
застарів, замість того щоб лишити його зеленим.

## Цикл

Два PR на хвилю: окремо планом, окремо роботою. Кожен етап оператор запускає
однією командою; далі веде інструмент.

```
ПЛАН                                гілка plan/0007-session-loop

  /keel-plan session-loop           оператор кличе
      keel new wave                   каркас файлу
      агент пише                      навіщо → сценарії → трансформи з файлами
      агент питає                     нез'ясоване — питанням, а не здогадкою
      keel gaps                       чого бракує
  PR → людина читає → merge         схвалення = план у головній гілці

РОБОТА                              гілка 0007-session-loop

  /keel-work                        один виклик — одна трансформа
      keel next                       трансформа, файли, межі, сценарії, контракти
      агент робить                    рівно у названих файлах
      keel check                      що не так зараз
      git commit                      слаг трансформи в повідомленні
  ⟳ поки keel next дає наступну

  /keel-review                      повний check і питання «про що промовчали»
  PR
```

`keel next` віддає **пакет**: усе, що потрібно для одного ходу, і нічого понад
те. Агент не відкриває документів навколо — він отримує зріз і працює з ним.

Етап не треба памʼятати. Хук старту сесії питає інструмент, у якому стані хвиля,
і вкидає відповідь у контекст разом з іменем потрібного скіла.

Агент не памʼятає нічого між ходами, і це навмисно: в автономному прогоні
контекст однаково обнуляється. Етапи не зникли — вони стали станом, який
виводиться, замість сторінки, яку треба тримати в голові.

## Установка

```bash
curl -fsSL https://raw.githubusercontent.com/Codcore/keel/main/install.sh | sh
```

Клонує репозиторій у `~/.keel` і кладе команду `keel` у `~/.local/bin`. Щоб
оновитись, запустіть той самий рядок ще раз — другий запуск це `git pull`.
`KEEL_REPO`, `KEEL_HOME` і `KEEL_BIN` перевизначають усі три шляхи.

Одного викачаного файла не досить: `keel init` копіює довідники в проєкт поруч
з інструментом, тож репозиторій має десь лежати цілим.

**Звідси два рівні, і їх легко переплутати.** `~/.keel` — дім методики, ваш клон
репозиторію; `keel/` у проєкті — копії, які туди поклав `init`. Оновлюються вони
різними командами:

| що оновлюється | чим | звідки бере |
|---|---|---|
| дім `~/.keel` | той самий рядок із `curl` ще раз | GitHub |
| копії в проєкті | `keel update` | з дому |

`keel update` **нічого не тягне з мережі** — він лише переносить у проєкт те, що
вже лежить удома. Тож коли методика вийшла новою версією, спершу оновлюють дім,
і аж тоді проєкт.

Далі, у проєкті, над яким працюєте:

```bash
keel init
```

Потрібні git і Python 3. Більше нічого.

**Лише стандартна бібліотека, і це не аскеза.** Методика від мови проєкту не
залежить, тож інструмент теж не має; Python є на кожній машині й у кожному CI.
YAML тут — вузька підмножина (ключі, списки, дві вкладеності), і власний читач
на сотню рядків дешевший, ніж `pip install` на початку кожного проєкту.
Інструмент, який тримає методику, не має сам бути залежністю.

Тести:

```bash
python3 -m unittest discover -s tests -t .
```

Розкладені за тим, що перевіряють: `test_yamlish`, `test_documents`,
`test_scope`, `test_adapters`, `test_commands`, `test_git_hooks`,
`test_agent_hooks`, `test_skills`, `test_setup`, `test_ci`, `test_modes`,
`test_language`, `test_install`, `test_agents`. Кожен запускається окремо
(`python3 -m unittest tests.test_scope`), спільна фікстура — в `tests/support.py`.
Тести нікуди не копіюються, тож ділити їх нічого не коштує — на відміну від
самого інструмента.

Один тест необовʼязковий: якщо в системі є PyYAML, він читає породжені шапки
скілів справжнім парсером. Свій читач поблажливий, а шапку читатимуть Claude і
Cursor — не він.

## Команди

| Команда | Що робить |
|---|---|
| `keel new wave <slug>` | каркас файлу: шапка з порожніми полями й секції-заготовки |
| `keel new contract <slug>` | те саме для контракту: `module` з `exports` або `verify` |
| `keel gaps [хвиля]` | чого бракує в описі хвилі: слаги без секцій, трансформи без файлів, сценарії без `proves`. І питає про забуте ребро: хвиля оголошує файл, який оголошує й інша хвиля, а `depends_on` її не називає |
| `keel next` | **пакет** наступної дії: трансформа, її файли й межі, сценарії, які вона наближає, тіла контрактів, на які спирається — і нічого зайвого. На головній гілці натомість називає хвилю, готову до роботи, і гілку, яку взяти. Markdown; `--json` для скриптів |
| `keel check` | усі перевірки — повний гейт. `--fast` лишає ті, що не запускають нічого, `--no-tests` пропускає прогін тестів і команду CI, `--branch` називає гілку там, де git її не знає, `--json` для скриптів |
| `keel rev` | показує редакції, які розійшлися; `--write` вписує нові; закритих хвиль не чіпає й каже про це |
| `keel show` | хвиля так, як її читає людина: навіщо, сценарії й трансформи, із позначками що закрито |
| `keel hooks` | показує стан `pre-commit` і `pre-push`; `--install` ставить, `--force` перезаписує чужий |
| `keel skills` | перепороджує скіли з методики |
| `keel init` | ставить Keel у проєкт: теки, копію інструмента, довідники, `AGENTS.md`, CI, хуки. `--docs` і `--lang` задають мови, `--adapter` називає мову проєкту, `--mode` — скільки себе ставити, `--ci` — власний заслон проєкту, `--agents` — кому ставити скіли й хуки, `--force` перезаписує чужий хук |
| `keel hook <подія> --agent` | відповідає хукові агента; кличеться конфігом, не руками |
| `keel update` | оновлює копії методики в проєкті. `--diff` показує різницю, `--force` перезаписує й правлене руками |

`gaps` і `check` різні саме тому, що сценарій без тесту на етапі планування
нормальний, а перед PR — ні. Одна команда з двома режимами плутала б обидва.
І жодна з них не планує: `gaps` каже, чого бракує, `check` — що не так.

## CI — команда, яку називає проєкт

Keel звіряє документи з фактами. Чи збирається проєкт, чи проходить свій лінтер
і свій набір — справа самого проєкту, і команду знає тільки він. Тому він її
**називає**, а умова одна: команда пройшла. Та сама форма, що вже є в `verify`
контракту, і з тієї ж причини: хто дає обіцянку — байдуже, важливо, що її можна
перевірити.

Ключ `ci` в `keel/keel.json`, і три стани:

| значення | що це означає | що робить `check` |
|---|---|---|
| `"mix ci"` | команду названо | виконує; впала — червоне |
| `""` | **ніхто не вирішив** | щоразу каже це вголос, але червоним не робить |
| `"none"` | свідома відмова | мовчить |

Середній стан — увесь сенс. Злиття, що пройшло без жодного власного прогону
проєкту, і ніхто про це не знає, — та сама тиша, проти якої стоїть решта
інструмента. Проєкт без CI лишається зеленим, але тільки якщо це сказано
вголос. Відмова — не мовчання; за цим правилом уже живуть розрізи якості.

Адаптер **пропонує** команду там, де в мови є домовленість: для Elixir це
`mix ci`. Для Python такої домовленості немає, і вигадувати її означало б
віддати оператору команду, яка ніколи не була правдою, — тож там порожньо, і
про це сказано. `keel init --ci "<команда>"` задає її одразу.

Виконується у повному `check`, не в `--fast`: коміт може бути проміжним, пуш і
мерж — ні. Отже це автоматично отримують pre-push, CI-воркфлоу і `/keel-review`.

На гілці `plan/*` `check` знає, де він. Перевірки 5 і 6 там не запускаються —
коду на гілці плану немає за задумом, — а замість них виконується `gaps`. Без
цього гілку плану не можна було б ні запушити, ні змержити: pre-push і CI
ганяють повний `check`, дві перевірки падали б завжди, і червоне на плановому PR
швидко перестало б щось означати. У `--fast` цього немає навмисно: коміт на
гілці плану може бути недописаним, а пуш і мерж — ні.

Прапорець `-C DIR` каже, де працювати. Корінь проєкту шукається вгору по теках:
перша, що має `keel/waves/`, або перша з `.git`.

## Дві мови, і вони незалежні

`keel init` записує в `keel/keel.json` два з них — третє це режим, — і плутати
ці два не варто:

| Ключ | Що визначає | Прапорець |
|---|---|---|
| `docs` | якою мовою довідники лягають у проєкт | `--docs uk\|en` |
| `lang` | чим агент пише хвилі й комміти, і які фрази ловлять скіли | `--lang uk\|en` |
| `ci` | власний заслон проєкту — команда, `""` якщо не вирішено, `"none"` як відмова вголос | `--ci "<команда>"` |
| `agents` | кому класти скіли й хуки: `claude`, `cursor`, `keel-agent`. Порожньо — нікому | `--agents <перелік>` |

Третій у переліку агентів — `keel-agent` — типово вимкнений. Він наш і поки
нічий більше, а теці `.keel-agent/` у чужому репозиторії робити нічого, доки
того інструмента там немає. Хуки й скіли він читає за контрактом Claude, тож
формат той самий, різна лише адреса.

Розділені вони тому, що хотіти англійський довідник з українськими тригерами —
нормально. Тіло скіла не залежить від жодного з них: його читає модель, і воно
завжди англійською. Так само англійське й те, що не читає ніхто з двох: workflow
для CI і скрипти git-хуків, включно з повідомленням, яке бачать на зламаному
пуші.

Ці два, режим, адаптер, перелік агентів, перевизначення агентських хуків і
команда CI — ось що
Keel тримає у файлі налаштувань, плюс хеші кожного породженого ним файла, але не все, що там
може лежати: файл ваш, він у вашому репозиторії, і ключі, яких Keel не знає,
переживають перезапис. Жодна з мов не вгадується: мова прози проєкту — рішення
команди, а не властивість коду.

`lang` вирішує ще й те, якою мовою говорить сам інструмент і якою мовою `keel
new` пише каркас хвилі чи контракту. Поля шапки в каркасі однакові завжди — вони
стають кодом, — а підказки й заголовок «Навіщо» йдуть мовою проєкту; читач
приймає обидва написання, тож проєкт може змінити мову, а наявні хвилі лишаться
читаними. Повідомлення інструмента ключуються англійським текстом, тож
пропущений переклад дає читабельну англійську, а не помилку. Командний рядок в обох випадках лишається англійським:
назви прапорців, метазмінні й `--help` — це словник самого інтерфейсу.

**Українська — джерело, англійська на нього спирається.** Джерело лежить у
`docs/uk/`, а англійський переклад — у корені репозиторію, бо саме його відкриває
той, хто прийшов уперше. Що є джерелом і що лежить на видноті — різні питання.

Редакція, на яку спирається кожен переклад, записана в `docs/revisions.json`, а
не в шапці самого файла: `README.md` у корені — обличчя репозиторію, і службова
шапка малювалася б таблицею над першим його рядком. `keel update` червоніє, коли
джерело змінилось, а переклад ні. Це те саме правило, що тримає тести й
контракти: хто спирається, той тримає редакцію. Двомовні документи гинуть саме
від того, що переклад тихо застаріває.

## Адаптери мов

Дві перевірки з шести залежать від мови: чим запускати тести (5) і звідки брати
експорти модуля (6). Адаптер вибирається за маркером у корені проєкту.

| | Elixir | Python |
|---|---|---|
| маркер | `mix.exs` | `pyproject.toml`, `setup.py`, `setup.cfg` |
| тести | `mix test` | unittest по всіх `test_*.py` і `*_test.py`, завантажених за шляхом |
| де тести | `test/**/*_test.exs`, `apps/*/test/**` | `tests/**/test_*.py`, `*_test.py` |
| тег сценарію | `@tag proves: :slug, rev: "a3f1c0"` | `# proves: slug, rev: "a3f1c0"` |
| експорти | `mix run --no-start` питає `__info__(:functions)` | імпорт модуля, `__all__` або публічні імена |
| типи | `Code.Typespec.fetch_specs` — цілий `@spec` перевіряється | немає: обіцяна форма позначається неперевіреною |
| кроки CI | `erlef/setup-beam` плюс `mix deps.get` | `actions/setup-python` |

Слаг сценарію й імʼя в тезі звіряються нормалізовано, тож `finishes-when-no-tool`
у кроці й `:finishes_when_no_tool` у тесті — те саме.

Версії для CI беруться з машини: `keel init` питає `elixir --version` там, де
його запустили, і вписує знайдене. Там, де питати нема кого — а це рівно
випадок `--adapter elixir` у порожньому репозиторії, — він бере закріплену пару,
і саме вона їде у workflow. Якщо ваш проєкт стоїть на іншому — поправте там.

**Кроки мови в CI стоять під умовою `hashFiles`, і не дарма.** Мову можна
назвати раніше, ніж зʼявиться її маркер — вписати адаптер у `keel.json` наперед
або дати `init --adapter` у порожньому репозиторії. Тоді `mix deps.get` побіг би
на гілці, де `mix.exs` немає, а це кожна гілка плану за задумом, і CI був би
червоним із причини, що гілки не стосується. З умовою кроки просто не
виконуються, доки маркера немає.

**Коли маркерів у корені більше за один, Keel не вгадує.** Проєкт із `mix.exs` і
`pyproject.toml` — це питання, а не перший рядок списку: від відповіді залежить,
чиї тести ганяються і в кого питати експорти. Перевірки 5 і 6 називають обидві
мови й ту, яку взято, і кажуть, як це закрити:

```json
{ "adapter": "elixir" }
```

Те саме дає `keel init --adapter elixir`. Обране пишеться в `keel/keel.json`, і
його ж читає генератор CI — інакше проєкт домовився б про мову, а workflow
ставив би іншу.

Мови без адаптера ламають не весь `check`, а рівно перевірки 5 і 6, і кажуть про
це прямо. Новий адаптер — це клас, успадкований від `Adapter`, із маркером,
командою тестів, регуляркою тега й способом дістати експорти. Успадкування тут не
формальність: у базовому класі лежить `supports_specs = False`, і саме воно
змушує перевірку сказати «ця мова про типи не відповідає» замість зеленої
позначки над необіцяним. Мова, яка вміє, ставить `True` — і тоді `exports()`
повертає ще й специфікації.

### Експорти, короткі й довгі

Яку форму дозволено писати — §2.9. Тут те, як перевірка її читає.

```yaml
exports:
  - "run(binary(), keyword()) :: {:ok, term()} | {:error, term()}"
  - "halt/1"
```

Кожен перевіряється за тим, що в ньому сказано. `run/3` каже, що функція є з
такою арністю. Сигнатура каже те саме — арність рахується з аргументів — і ще,
там де адаптер уміє читати типи, що модуль оголошує саме цей `@spec`. На
розбіжності перевірка друкує те, що оголошує модуль, у тій формі, в якій це
пишуть руками, тож виправлення — це копіювання. Функцію зовсім без `@spec`
перевірка називає, а не пропускає; так само й форму, обіцяну мовою, адаптер якої
типів не читає, — сьогодні це Python.

**Аргументи можна називати.** `run(text :: binary(), opts :: keyword()) :: :ok` —
саме так віддає їх компілятор, і саме так їх зазвичай і пишуть. Роздільником
вважається `::` поза дужками, тож імена всередині нічого не ламають.

**Кілька `@spec` на одну функцію — кілька чесних обіцянок.** Контракт може
назвати будь-яку з них, і перевірка зелена, якщо збігається хоч одна. Друкує вона
на розбіжності всі, а не першу-ліпшу:

```
✗ обіцяна форма pick/1 не збігається з тим, що оголошує модуль:
      pick(integer()) :: :small
      pick(binary()) :: :big
```

**Різницею є тип, а не набір.** Перед звірянням обидва боки стискаються однаково:
переноси зникають, пробіли біля дужок теж, після коми лишається рівно один, довкола
`|` — по одному. Компілятор пише `run( binary() )`, людина пише `run(binary())`, і
це те саме. `{:ok,term()}` і `{:ok, term()}` — теж.

### Контракт із `verify`

Адаптера він не потребує — там команда. Вона має бути рядком, інакше перевірка
червоніє замість мовчки її проминути, і на неї є межа в 30 секунд: обіцянка — це
проба, а не збірка, і зависла проба тримала б `pre-push` і CI скільки їм
дозволено працювати. Стандартний ввід їй закритий, щоб команда з підказкою падала
одразу, а не марно чекала. `--no-tests` не запускає ні її, ні пробу експортів:
проба імпортує модулі проєкту, а імпорт виконує все, що модуль робить при
завантаженні, — тож прапорець «нічого не запускати» тепер чесний до кінця.

**Межа стоїть на всьому, що виконує код проєкту**, а не лише на `verify`. Прогін
тестів має десять хвилин, проба експортів — дві. Фіксована команда адаптера не
безпечніша за команду з файла: `mix test` і той скрипт, що питає модуль про
експорти, обидва виконують чужий код, а перевірка 6 — це те, що ганяє `pre-push`.
Вичерпаний час — червона перевірка з назвою команди, а не тиша й не трейсбек;
відсутній інтерпретатор — так само.

**Тепер команд із файлів у репозиторії дві, і це варто знати.** `verify`
контракту й ключ `ci` в `keel/keel.json`. Друга ширша: `verify` виконується
лише в тих контрактів, які його оголосили, а `ci` — у будь-якого проєкту, який
його назвав, і `init` пропонує `mix ci` кожному еліксирному проєкту, у який
встановлюється. `keel check`
запускає її через оболонку, а `pre-push` запускає `keel check`. Отже клонувати
чужий проєкт або взяти гілку з PR і зробити `git push` означає виконати те, що
написано в його контрактах. Досі кожен підпроцес Keel був фіксованою командою
адаптера; ця — перша, яку задає той, хто писав контракт. Практичний висновок
один: контракт у чужому PR читають так само уважно, як код.

## Як Keel потрапляє в проєкт

Репозиторій `keel` — дім методики, а не те, що читає агент. Агент читає файли
**в проєкті, над яким працює**, і `keel init` їх туди кладе:

```
keel/waves/                     порожні теки
keel/contracts/
keel/keel.json                  налаштування: мови, режим, адаптер, кому ставити
keel/keel.py                    сам інструмент, копією
keel/METHODOLOGY.md             методика, копією
keel/README.md                  цей файл, копією
keel/QUALITY.md                 розрізи якості — їх проходять пунктами
AGENTS.md                       блок між маркерами: принципи й вказівники
.github/workflows/keel.yml      CI, породжений
.claude/skills/keel-*/SKILL.md  породжені
.cursor/skills/keel-*/SKILL.md  породжені — той самий формат
.claude/settings.json           хуки агента в режимі strict; чуже лишається
.cursor/hooks.json              те саме для Cursor
.keel-agent/skills/keel-*/…     і .keel-agent/settings.json — лише якщо
                                про цього агента попросили
.git/hooks/                     pre-commit і pre-push, що кличуть keel
```

**Інструмент їде копією**, і саме заради цього він один файл. CI піднімає чисту
машину на кожен пуш; викачує вона тільки репозиторій проєкту, тож `keel.py` має
бути в ньому, інакше перевіряти буде нічим. Заразом це знімає питання «а чи стоїть
keel у того, хто клонував».

Хук шукає інструмент по черзі: змінна `KEEL`, потім `keel` на PATH, потім копія
в проєкті, і останнім — абсолютний шлях того, хто ставив хук. Копія в
проєкті — єдина, яка завжди на місці; вкарбований шлях це запасний варіант для
чекауту, де копії немає, і саме тому `.git/hooks` не варто носити між машинами.

**Довідники їдуть копіями, і на кожен показує `AGENTS.md`.** Файл сам собою нічого
не змушує читати: змушують чотири речі — `AGENTS.md`, який читається завжди, хук
старту сесії, хук перед записом файлу і скіл, що вантажиться при плануванні.
Показати можна тільки на те, що лежить у цьому ж репозиторії. Файл, на який ніщо
не показує, — мертвий.

Читаються вони рідко, і це нормально: при роботі агентові потрібен пакет від
`keel next`, при плануванні — скіл. Але «рідко» не є «ніколи». Коли не ясно, що
йде в шапку трансформи або як рахується редакція, дивитись треба кудись.

**Принципи не окремий файл.** Сім тверджень — це десять рядків, і вони йдуть
у `AGENTS.md`, який агент читає завжди. Береться текст із `PRINCIPLES.md`, тож
розійтися їм нема як.

`AGENTS.md` **не створюється, а дописується**: блок між `<!-- keel:start -->` і
`<!-- keel:end -->`, решта файлу — проєктова, і оновлення її не чіпає. Проєкт
має власний `AGENTS.md` майже завжди, і перезаписувати його означало б відбирати.

`.claude/settings.json` так само зливається: чужі налаштування лишаються, наш
запис не дублюється при повторному `init`, а якщо файл побитий — інструмент його
не чіпає й каже про це.

Скіли кладуться **тим, кого назвали** в налаштуванні `agents` — типово обом
відомим агентам, бо вони дешеві, а яким працюватимуть завтра, невідомо. Третій,
`keel-agent`, ставиться лише на прохання, і порожній перелік — теж відповідь.

**`init` комітить те, що поклав** — окремим коммітом і додаючи в індекс лише
власні файли, тож ваші незакомічені зміни поруч лишаються вашими. `--no-commit`,
якщо волієте самі. Без git він взагалі відмовляється: Keel увесь стан читає з
git, і заводити комусь репозиторій — більше рішення, ніж поставити методику.

**Агента запускають у самій теці проєкту.** Скіли беруться з теки старту й
батьківських; ті, що лежать нижче, підхоплюються аж тоді, коли агент прочитає
там якийсь файл.

Одразу після установки перший виклик може відповісти «Unknown skill» — скіли ще
не підхопились. Лікується `/reload-skills` або просто повторним викликом; сесію,
відкриту до установки, треба перезапустити, бо `/clear` теку на облік не бере.

**Гілка плану може нести файли самого Keel.** Правило «план не чіпає код»
стосується коду проєкту, а не того, що поклав `init`: інакше воно замуровувало б
першу хвилю щоразу, коли `init` чи `update` щось освіжили.

**Оновлення не затирає роботу.** `keel init` записує в `keel/keel.json` хеш
кожного породженого файла, і саме це дає `keel update` змогу відрізнити «методика
поїхала вперед» від «цей файл правили руками». Перше оновлюється мовчки, друге —
ні: `update` називає такий файл, лишає його як є і виходить із ненульовим кодом.

Питати він не питає навмисно. Питання спиняє автономний прогін, мовчазний
перезапис нищить роботу; відмова по одному файлу не робить ні того, ні того.
`--diff` показує різницю, `--force` перезаписує.

`AGENTS.md` і `.claude/settings.json` у цьому обліку не беруть участі: Keel
володіє в них блоком, а не файлом, тож вони зливаються, а не заміняються.

Тут же живе перевірка перекладів: `update` червоніє, коли англійський довідник
відстав від українського джерела. У `check` її немає навмисно — перевірки
про граф хвиль у проєкті, а ця про копії самої методики.

## Хуки git

Те, на чому все тримається. Працюють незалежно від агента й від того, чи він
щось прочитав.

| Хук | Що робить |
|---|---|
| `pre-commit` | швидкі перевірки: посилання, цикли, редакції, scope, заголовки |
| `pre-push` | повний `keel check` разом із тестами й експортами |
| CI | те саме, що `pre-push` — на випадок, якщо хук обійшли |

Швидке — на комміт, повільне — на пуш: агент комітить часто й не має чекати
хвилинами, а червоне все одно не доїде до головної гілки.

Чужий хук не затирається без `--force`.

CI відрізняється двома дрібницями, і без них він тихо зелений. Голова там
відчеплена, тож імʼя гілки передається як `--branch`; головної гілки локально
немає, вона є як `origin/main`. Історію треба качати всю — межі звіряються з
місцем, де гілка відійшла.

## Хуки агента

Швидший зворотний звʼязок. Вони не заміна git-хукам: агентський хук робить
помилку дешевшою, `pre-commit` робить її неможливою.

| Подія | Що робить | Claude | Cursor | keel-agent |
|---|---|---|---|---|
| старт сесії | вкидає стан і називає скіл | `SessionStart` | `sessionStart` | `SessionStart` |
| перед записом файлу | відмовляє, якщо файл не оголошений | `PreToolUse` | `preToolUse` | `PreToolUse` |

Друга подія найцінніша: дрейф ловиться в мить, коли агент збирається писати не
туди, а не через комміт.

Імена подій збігаються, конфіги всі проєктові й усі комітяться. Розходиться те,
чим хук відповідає:

| Що | Claude | Cursor | keel-agent |
|---|---|---|---|
| відмова | `hookSpecificOutput.permissionDecision: "deny"` | `permission: "deny"` | як у Claude |
| текст у контекст | `additionalContext` | `additional_context` | як у Claude |
| обгортка | `matcher` і вкладений список `hooks` | плаский список, `"version": 1` | як у Claude |

Вихід із кодом 2 блокує дію в усіх трьох — це єдине спільне. Третій говорить
контрактом Claude навмисно: власних подій він не заводить, тож і діалекту свого
не має. **Codex тут немає**, і це не забуття — його `apply_patch` ще не
розібрано, тож писати про відмову, якої інструмент не вміє надіслати, було б
описом неіснуючого.

Звідси форма породженого: **один скрипт, кілька конфігів**. Конфіги кличуть той
самий `keel hook` із прапорцем, який каже, чиїм діалектом відповідати. Інакше
скрипти розійшлися б: те, що пишуть окремо, окремо ж і застаріває.

### Хук старту показує на скіл

Скіл — це файл з інструкціями, який агент бере сам, коли вирішить, що доречно.
Хук — програма, яку запускає сам Claude чи Cursor, і агент на це не впливає.

Хук не може завантажити скіл: він може лише **вкинути в контекст текст**. Тому
`keel hook session` дивиться в git і друкує речення, яке називає потрібний скіл:

| Стан | Що каже |
|---|---|
| гілка `plan/*` | візьми `keel-plan` |
| головна гілка | хвиля, готова до роботи, і гілка, яку взяти, або що час планувати |
| файл хвилі не читається | причина, і більше нічого |
| плану ще немає на головній | роботи немає: схвалення не сталося |
| є відкрита трансформа | візьми `keel-work`, ось пакет `next` |
| усі трансформи закриті | візьми `keel-review` |
| гілка не є хвилею | візьми `keel-plan`, ось як почати |

Сенс у тому, що етап знає git, а не агент. Без цього агент мав би здогадуватись.

У режимі `manual` це речення звертається не до агента, а через нього до людини:
брати скіл сам він там не має права, і сказати йому «візьми» означало б
заблокований виклик. Тому текст каже «попроси набрати /keel-plan».

### Хук перед записом

Порівнює файл із оголошеними у кроці — навмисно з тими самими, що звіряє
перевірка 4, щоб хук не був суворішим за гейт.

**На головній гілці він відмовляє запис у код.** Не через скоуп — порівнювати
там нема з чим: перевірка 4 звіряє гілку **з** `main` і, стоячи на самому
`main`, чесно повертає порожньо. Саме тому єдина гілка, де за планом нічого не
роблять, лишалась єдиною, де можна було писати все. Тепер хук каже, що `main` —
це куди готова робота приїжджає, і відсилає на гілку хвилі. Меблі Keel вільні
завжди, а проєкт, у якому ще немає жодної хвилі, не замуровується: плану, з
якого працювати, там просто нема.

Шлях у вхідному JSON лежить по-різному, і документація нерівна. У Claude це
`tool_input.file_path` для Write, Edit і NotebookEdit — документовано. У Cursor
документації на інструменти запису немає; `file_path` стоїть у сусідніх
`beforeReadFile` та `afterFileEdit`, і звіт про ваду каже, що для Write
застосовується воно ж. Тому шлях шукається серед кількох імен, а `tool_input`
розбирається і як обʼєкт, і як рядок із JSON усередині — для частини інструментів
Cursor віддає його саме так.

**Коли шлях не знайшовся, хук каже це вголос і перелічує оголошені файли.**
Мовчазний пропуск виглядав би як перевірка, якої не було.

Codex поки без хуків: запис іде через `apply_patch`, і шлях лежить усередині
тексту патча, а не полем. Його хуки ще й вмикаються в `config.toml` через
`[features] hooks = true` і не працюють на Windows.

## Три режими

Файл скіла і слеш-команда — це один обʼєкт в обох агентах. Хто до нього дістане,
вирішує один рядок у шапці: з `disable-model-invocation: true` процедуру починає
лише людина, набравши `/keel-plan`, а опис зникає з контексту моделі зовсім; без
цього рядка модель читає опис і може взяти процедуру, коли вважає момент
слушним. Власна міграція Cursor переводить старі слеш-команди у скіли саме з цим
рядком.

Тобто питання не «скіли чи команди». Питання — хто починає процедуру і чи
стежить хтось, поки вона йде. `keel init --mode` відповідає на обидва одним
словом:

| Режим | Хто починає процедуру | Агентські хуки |
|---|---|---|
| `strict` (типово) | агент, на власний розсуд | ставляться |
| `soft` | агент, на власний розсуд | немає |
| `manual` | тільки ви, набравши `/keel-plan` | немає |

Типовий — `strict`, бо методика, якої ніхто не починає, не методика.

**Хуки в тій колонці — агентські**: ті, що читають, що агент збирається писати, і
відмовляють у файлі, якого хвиля не оголошувала. Git-хуки — інший звір і ставляться
за будь-якого режиму: вони бережуть репозиторій від зламаної хвилі, що доїде до
віддаленої гілки, і від вас теж.

Три слова покривають три позиції й гублять четверту: починати кожну процедуру
руками, але лишити охорону, яка не дасть писати повз оголошене. `--agent-hooks`
і `--no-agent-hooks` перекривають режим, тож ця комбінація лишається досяжною:

```bash
keel init --mode manual --agent-hooks
```

Якщо `keel/keel.json` не читається, `init`, `skills` і `update` відмовляються
працювати, поки його не полагодять: діяти за замовчуваннями означало б
переписати український проєкт англійською й затаврувати незаймані копії як
правлені руками. Хуки натомість відповідають і з битим конфігом — їм мовчати не
можна.

Режим записується в `keel/keel.json`, і `keel skills` та `keel update` його
читають — перегенерація ніколи не поверне ні процедури моделі, ні хуки, яких
режим не хотів. Змініть режим у тому файлі руками — наступний `update` хуки
зніме, а не просто утримається від додавання. Прапорці `--agent-hooks` і
`--no-agent-hooks` записуються туди ж: перекриття переживає оновлення, а не
живе до першого `update`.

**Звузити режим — це і зняти те, що ставив ширший.** `keel init --mode manual`
поверх strict не просто перестає писати хуки: він прибирає `.cursor/hooks.json` і
вилучає наші записи з **обох** файлів налаштувань — Клодового й `.keel-agent/` —
лишаючи все чуже в них недоторканим. Файл, у якому після цього не лишилось
нічого, крім порожнього обʼєкта, зникає разом із ними: `{}` — це наш слід, а не
чиясь конфігурація. Інакше вивід казав би «агентських хуків немає», поки хуки далі
відмовляють у записі — а звіт, який спростовує файлова система, це рівно те, проти
чого весь цей інструмент.

Файл, якого ми не писали, знімати не наше діло: якщо `.cursor/hooks.json` більше
не збігається з тим, що клав Keel, він називається і лишається — та сама
відповідь, яку `update` дає відредагованому руками файлу.

## Скіли

Скіл потрібен там, де є судження. Судження в Keel одне — **планування**: як пройти
розрізи якості, як відрізнити сценарій від межі, як зрозуміти, що трансформа ще
не атомарна. Це не виражається командою.

Робота веде себе сама: `next` каже дію, `check` каже проблему. Там скіл був би
переказом того, що інструмент і так друкує. Отже один змістовний скіл —
`keel-plan`, і два тонкі — `keel-work` та `keel-review`.

| Інструмент | Куди кладеться |
|---|---|
| Claude Code | `.claude/skills/<name>/SKILL.md` |
| Cursor | `.cursor/skills/<name>/SKILL.md` |
| keel-agent | `.keel-agent/skills/<name>/SKILL.md`, за вибором |
| Codex і решта | `AGENTS.md`, десять рядків із вказівниками |

Формат один і той самий: `name`, `description`, необовʼязковий `paths`. Cursor
має ще й правила `.cursor/rules/*.mdc`, але вони для коротких постійних
обмежень, а тут багатокрокові процедури — це скіли.

**Скіл бере не лише модель.** Імʼя теки і є командою, тож оператор запускає етап
циклу сам — а в режимі `manual` тільки він і запускає:

| Скіл | Коли | Що під ним запускається |
|---|---|---|
| `/keel-plan <слаг>` | починається нова робота | `keel new wave`, `keel rev --write`, `keel gaps` |
| `/keel-work` | план злитий, пишемо код | `keel next`, `keel check` |
| `/keel-review` | перед PR | `keel check` |

Слова в лівій колонці й слова в правій навмисно різні. Ліворуч — **стадії**
циклу, і саме так вони звуться в `METHODOLOGY.md`; праворуч — **дії** інструменту. Одна
стадія це кілька дій, тож звести їх до однієї назви не вийде: `/keel-plan` не
дорівнює `new wave`, він дорівнює трьом командам і всьому міркуванню між ними.
Оператор знає три слова ліворуч; решта — словник агента.

Опис — це головний механізм спрацювання, тож у ньому лежить **уся інформація про
те, коли скіл брати**, а в тілі — лише що робити. Написаний він навмисно
наполегливо: моделі схильні *недо*спрацьовувати й не брати скіл там, де він
доречний. Опис береться в лапки, бо містить двокрапку, і обрізається на 1536
знаках у переліку Claude.

**`paths` не має жодний із трьох, і це навмисно.** Поле звужує скіл до файлів,
про які він, — але поки на старті сесії під шаблон не підпадає нічого, скіл
зникає з переліку взагалі, а не просто перестає підхоплюватись сам. Перевірено
наживо: із порожньою `keel/waves/` команди `/keel-plan` не існувало, доки два її
брати без `paths` були на місці. А привʼязати до хвиль саме той скіл, що пише
**першу** хвилю, — значить сховати його рівно тоді, коли він потрібен.

**Ці файли породжуються командою `keel skills`, а не ведуться руками.** Тіло в
обох однакове, різняться лише поля, яких другий не знає, і тест це стереже.

## Стан

Зроблено: усі перевірки, `new`, `gaps`, `next`, `rev`, `check`, `hooks`,
`skills`, `init`, `update`, `hook`; git-хуки й CI; три скіли у двох діалектах;
хуки агента для Claude і Cursor; довідники двома мовами із замком на редакції.

Лишилось:

1. **Хуки для Codex** — відкладені: запис іде через `apply_patch`, і шлях лежить
   усередині тексту патча, а не полем.
2. **Перша справжня хвиля на `keel-agent`** — доти методика перевірена
   інструментом і тестами, але не роботою.

## Відкрите

- **Чи справді Cursor зве це поле `file_path`.** У Claude воно документоване, у
  Cursor — ні: доказ непрямий, зі звіту про ваду й із сусідніх подій. Хук шукає
  серед кількох імен і мовчки не пропускає, тож перший запуск у Cursor скаже
  правду; тоді список можна звузити.
- **Чи приходить `tool_input` рядком і для вбудованих інструментів.** Для MCP це
  видно в захоплених прикладах; читач розбирає обидві форми.
- **Скільки насправді коштує хвиля.** Сорок розрізів на маленьку трансформу
  можуть виявитись задорогими, а хук перед записом — заважати більше, ніж
  допомагати. Це видно тільки з першої справжньої хвилі.
