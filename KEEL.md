# Keel

Методика розробки з агентом: **три типи документів, шість перевірок**.
Наступниця `ATOMIC_DEVELOPMENT.md`, у якій вісім типів атомів і вісімнадцять чеків.

**Статус: чернетка. У цьому репозиторії не застосована.** `atomic-dev` лишається
на старій методиці; Keel пробується на іншому проєкті, де нема чого конвертувати.

Принципи — одна сторінка, `keel/PRINCIPLES.md`, читається завжди. Цей файл —
довідник, читається за потреби.

## Мова й формат

Шапка документа — англійською: її поля йдуть у код, теги тестів та імена файлів.
Проза — українською: її читає і схвалює людина.

Шапка — YAML між трьома рисками. Тіло — звичайний Markdown.

## Де що лежить

```
KEEL.md                  методика (цей файл)
keel/PRINCIPLES.md       одна сторінка принципів
keel/QUALITY.md          дев'ять розрізів якості — чекліст при написанні кроку
keel/steps/              кроки — один файл на гілку
keel/contracts/          контракти — один файл на контракт
keel/decisions/          рішення, на які спираються два кроки й більше
```

Так виглядає **проєкт, який живе за Keel**. У домі самої методики — репозиторії
`keel` — ці три файли лежать у корені, бо вони тут джерело, а не копія.

Ідентифікатор — це імʼя файлу без розширення. Якорів усередині документів немає,
тож перевірка «посилання веде кудись» — це наявність файлу, а не парсер.

## Три сутності

### Крок

Один файл, одна гілка, один PR. Усередині:

- **сценарії** — що обіцяємо. Кожен стає тестом;
- **трансформи** — чим це робиться. Кожна стає коммітом.

Обидва живуть як секції в тілі; їхні імена й звʼязки — у шапці.

### Контракт

Що код обіцяє іншому коду: модуль, експортовані функції, сенс. Окремий файл,
бо живе довше за крок, який його створив.

### Рішення

Окремий файл — тільки коли на нього спираються **два кроки й більше**.
Важливе для одного кроку живе в його тілі. Правило машинне: рахуєш посилання.

## Звʼязки

| Ребро | Звідки куди | Навіщо |
|---|---|---|
| `depends_on` | крок → крок | порядок роботи |
| `proves` | сценарій → контракт | у контракту є доказ |
| `contracts` | трансформа → контракт | що реалізує, плюс редакція |
| `implements` | трансформа → сценарій | який комміт наближає яку обіцянку |
| тег у тесті | тест → сценарій | обіцянку доведено, і саме цю її редакцію |

Ті самі ребра, що були в старій методиці, тільки в шапці, а не в прозі.
Головний біль давало не ребро, а спосіб запису: жирний код плюс якір плюс
відносний шлях — три речі, які розходяться окремо.

## Scope: точні файли

Трансформа перелічує файли поіменно, до роботи. Глоби не використовуються:
під глобом агент наплодить десять файлів там, де треба один, і ніщо не писне.

- крок власного scope не має — він сума трансформ;
- перевірка йде **в обидва боки**: чіпнув поза списком видно, оголосив і не чіпнув теж;
- перевіряється **вся гілка**, не окремий комміт;
- розширення списку дозволене й лишається рядком у diff. Дрейф не заборонений — названий.

## Редакції

Посилання може нести редакцію того, на що показує, — короткий хеш тексту.
Перевірка звіряє її з тим, що написано зараз.

```
@tag proves: :finishes_when_no_tool_called, rev: "a3f1"   тест → сценарій
contracts: [session-run@7c40de]                            трансформа → контракт
```

Перше ловить «сценарій переписали, тест лишився старим і зеленим».
Друге — дзеркальне: «контракт переписали, код лишили».

**Редакція міняється від будь-якої зміни слова.** Перед хешуванням згортаються
тільки повторні пробіли й переноси рядка; кома, регістр і перефразування дають
нову редакцію, і тест доводиться перечитати.

У шапці кроку редакцій сценаріїв немає: текст лежить у тілі, хеш рахується з нього
на льоту. Редакцію вписує лише той, хто спирається.

## Закриття виводиться

Жоден статус не пишеться руками.

| Що | Закрите, коли | Звідки видно |
|---|---|---|
| Трансформа | у гілці є комміт, чиє повідомлення несе її слаг, і файли комміта збігаються з оголошеними | git log, git diff |
| Сценарій | є тест із його імʼям, він зелений, редакція збігається | прогін тестів, текст кроку |
| Контракт | редакція збігається з записаною і модуль експортує обіцяне | файл, зібраний модуль |
| Крок | усі трансформи закриті, усі сценарії доведені, шість перевірок зелені | усе вище разом |

## Шість перевірок

1. Посилання ведуть кудись: кожен слаг у шапці має свій файл або свою секцію.
2. `depends_on` без циклів.
3. Редакції контрактів збіглися з поточним текстом.
4. Файли, змінені гілкою, збігаються з оголошеними в трансформах — в обидва боки.
5. Кожен сценарій має тест зі своїм імʼям, тести зелені, редакція в тезі збігається.
6. Модулі експортують те, що обіцяють контракти.

Сьома, дрібна: множина імен у шапці збігається з множиною заголовків у тілі.

Жодна не парсить прозу: усі читають шапку, git і зібрані модулі.

## Чого немає

| Було | Куди пішло |
|---|---|
| Фіча, шар | нікуди. Порядок дає `depends_on`, «де робилось» — scope, межі архітектури — конфіг лінтера |
| Вимога (REQ) | сценарії. Вимога й сценарій — одна обіцянка, записана двічі |
| Питання (Q) | обговорення PR. Питання живе години, а не роки |
| Журнал (LOG.md) | git |
| Рядок `approved` | аппрув PR |
| Констрейнти як поле | перевіряєме — сценарій, структурне — scope, решта — абзац «межі» в трансформі |
| Номери сценаріїв | слаги. Номер зсувається при вставці, імʼя — ні |
| Теги | нікуди. Scope і так каже, чого стосується робота |
| Статуси руками | виводяться з git і тестів |

```markdown
## Навіщо

Одна розмова з моделлю проти набору інструментів, який дали ззовні.
Сесія не знає, які інструменти отримала — тому нею ганяються обидва шляхи,
і різниця між прогонами є різницею в інструментах.

## scenario: finishes-when-no-tool-called

**Given** початковий контекст і порожній набір інструментів,
**When** модель відповідає текстом без виклику,
**Then** розмова завершується станом `:finished`, а в записі є хід.

## transform: drive-turns-on-reqllm

Крутити ходи, доки модель кличе інструменти. Відповідь інструмента
дописується в запис перед наступним ходом.

Межі: лічильника спроб немає — відмова інструмента це відповідь,
і наступний хід є повтором.
```

## Імена

**Комміт називає трансформу слагом** у своєму повідомленні. Це єдиний звʼязок
між роботою і планом, і завдяки йому хеш проставляється сам.

**Номер у назві кроку** (`0007-`) — унікальний префікс, а не порядок. Порядок
виводиться з `depends_on`. Інакше зʼявляється спокуса перенумеровувати, і
посилання ламаються — та сама пастка, з якої вийшли, відмовившись від кодів.

## Розрізи якості

`keel/QUALITY.md` — девʼять характеристик ISO/IEC 25010 як список питань.
Він **чекліст, а не структура**: жоден крок не мусить мати сценарій на кожен
розріз. Агент проходить список і дає одну з трьох відповідей — не стосується,
відповіли ось цим сценарієм, промовчали. Промовчали означає: розріз доречний,
нічого його не закриває, і треба або сценарій, або рішення сказати «ні» вголос.

**Один прохід на крок**, там, де пишуться сценарії. Не на кожному рівні й не
до збіжності: рівнів більше немає, є крок.

Сенс не в повноті, а в тому, що випадок, якого ніхто не придумав, тепер не
можна проминути мовчки. Агент за замовчуванням пише щасливий шлях.

## Як Keel потрапляє в проєкт

Репозиторій `keel` — дім методики, а не те, що читає агент. Агент читає файли
**в проєкті, над яким працює**, і `keel init` їх туди кладе:

```
keel/steps/                     порожні теки
keel/contracts/
keel/decisions/
keel/QUALITY.md                 копія — його проходять пунктами
AGENTS.md                       блок між маркерами
.claude/skills/keel-*/SKILL.md  породжені
.cursor/rules/keel-*.mdc        породжені
.claude/settings.json           хуки агента, породжені
.cursor/hooks.json              те саме для Cursor
.codex/hooks.json               те саме для Codex
.git/hooks/                     pre-commit і pre-push, що кличуть keel
```

**Повна методика в проєкт не копіюється.** Чотириста рядків, однакових скрізь,
агент читає рідко: при роботі йому потрібен пакет від `keel next`, при плануванні —
скіл. Довідник живе вдома й доступний як `keel doc`.

**Принципи теж не окремий файл.** Сім тверджень — це десять рядків, і вони йдуть
у `AGENTS.md`, який агент читає завжди.

`AGENTS.md` **не створюється, а дописується**: блок між `<!-- keel:start -->` і
`<!-- keel:end -->`, решта файлу — проєктова, і `keel update` її не чіпає. Проєкт
має власний `AGENTS.md` майже завжди, і перезаписувати його означало б відбирати.

У блоці — сім принципів і три команди: де питати стан, що запускати перед
коммітом, де розрізи. Не переказ методики, а вказівник.

Скіли кладуться **обидва набори одразу**: вони дешеві, а яким агентом працюватимуть
завтра — невідомо. Далі їх перепороджує `keel skills`, коли методика змінилась.

**Усе, що потрапило в проєкт із методики, несе її версію** — і копії, і породжені
скіли з `AGENTS.md`. Інструмент знає свою версію; `keel check` попереджає — не
падає, — коли в проєкті лежить старіше, і радить `keel update`, який показує
різницю перед тим, як переписати. Він же ловить, якщо породжений файл правили
руками: тоді оновлення не затирає мовчки, а питає.

Методика застосовує до себе власне правило про редакції. Якщо воно не працює тут,
воно не працює ніде.

## Хто що робить

Правила не тримаються на тому, що агент їх прочитав: один читає, інший ні, і це
не лікується кращими інструкціями. Розподіл такий:

| Хто | За що відповідає |
|---|---|
| Інструмент | стан, каркаси, перевірки, «одна наступна дія» |
| Агент | текст: навіщо, сценарії, розбиття на трансформи, код |
| Хук | не дає пройти повз |
| Скіл | як думати там, де є судження — тобто при плануванні |

Коротко: **інструмент знає стан, агент має судження**. Інструмент не пише прозу —
у нього немає моделі. Агент не памʼятає правил — він питає інструмент.

## Команди

**Python-скрипт, лише стандартна бібліотека.** Методика від мови проєкту не
залежить, і інструмент теж не має; Python є на кожній машині й у кожному CI,
пишеться швидко й тестується просто.

Жодних зовнішніх пакетів: YAML тут — вузька підмножина (ключі, списки, дві
вкладеності), і власний читач на сотню рядків дешевший, ніж `pip install` на
початку кожного проєкту. Інструмент, який тримає методику, не має сам бути
залежністю.

| Команда | Що робить |
|---|---|
| `keel new step <slug>` | каркас файлу: шапка з порожніми полями й секції-заготовки |
| `keel new contract <slug>` | те саме для контракту |
| `keel plan` | повнота **плану**: чи всі слаги мають секції, чи трансформи мають файли, чи сценарії мають `proves` |
| `keel next` | **пакет** наступної дії: трансформа, її файли й межі, сценарії, які вона наближає, тіла контрактів, на які спирається — і нічого зайвого |
| `keel check` | шість перевірок — повний гейт |
| `keel rev` | перерахунок редакцій після правки сценарію чи контракту |
| `keel skills` | породжує файли інструкцій під кожен агент із цієї методики |
| `keel init` | ставить Keel у проєкт: теки, копії принципів і розрізів, `AGENTS.md`, хуки |
| `keel update` | оновлює копії методики в проєкті до версії інструмента, показавши різницю |

`plan` і `check` різні саме тому, що сценарій без тесту на етапі планування
нормальний, а перед PR — ні. Одна команда з двома режимами плутала б обидва.

## Цикл

Два PR на крок: планом і роботою.

```
ПЛАН                          гілка plan/0007-session-loop
  keel new step <slug>        каркас
  агент пише                  навіщо → сценарії (через QUALITY) → трансформи з файлами
  keel plan                   чого бракує
  PR → людина читає → merge   схвалення записане тим, що план у головній гілці

РОБОТА                        гілка 0007-session-loop
  keel next                   трансформа, файли, межі
  агент робить
  keel check                  що не так зараз
  git commit                  слаг трансформи в повідомленні
  ⟳ поки є відкриті трансформи
  PR
```

`keel next` віддає **пакет**, як `step_package` у PlanGraph: усе, що потрібно для
одного ходу, і нічого понад те. Агент не відкриває документів навколо — він
отримує зріз і працює з ним.

**Схвалення плану нікуди не пишеться — воно виводиться.** Файл кроку в головній
гілці означає, що людина його прочитала й пустила; `keel next` не віддає трансформ
із кроку, якого там ще немає. Ніяких полів і ніяких рядків журналу.

Агент не памʼятає нічого між ходами, і це навмисно: в автономному прогоні
контекст однаково обнуляється. Етапи не зникли — вони стали станом, який
виводиться, замість сторінки, яку треба тримати в голові.

## Хуки

Два ряди, і вони про різне.

**Хуки git** — те, на чому все тримається. Працюють незалежно від агента й від
того, чи він щось прочитав:

| Хук | Що робить |
|---|---|
| `pre-commit` | чотири швидкі перевірки: посилання, цикли, scope, редакції |
| `pre-push` | повний `keel check` разом із тестами й експортами |
| CI | те саме, що `pre-push` — на випадок, якщо хук обійшли |

Швидке — на комміт, повільне — на пуш: агент комітить часто й не має чекати
хвилинами, а червоне все одно не доїде до головної гілки.

**Хуки агента** — швидший зворотний звʼязок. Вони є в усіх трьох інструментах, і
формати конфігів різні, тож `keel init` кладе три файли, породжені з одного
джерела:

| Подія | Що робить | Claude | Cursor | Codex |
|---|---|---|---|---|
| старт сесії | виконує `keel next`, вкидає пакет у контекст | `SessionStart` | `sessionStart` | `SessionStart` |
| перед записом файлу | відмовляє, якщо файл поза межами трансформи | `PreToolUse` | `preToolUse` | `PreToolUse` |

Друга подія найцінніша: дрейф ловиться в мить, коли агент збирається писати не
туди, а не через комміт.

**Але сила лишається в git.** Хуки Codex експериментальні, вмикаються прапорцем і
не працюють на Windows; будь-який з трьох можна вимкнути. Агентський хук робить
помилку дешевшою, `pre-commit` робить її неможливою.

## Скіли

Скіл потрібен там, де є судження. Судження в Keel одне — **планування**: як пройти
розрізи якості, як відрізнити сценарій від межі, як зрозуміти, що трансформа ще
не атомарна. Це не виражається командою.

Робота веде себе сама: `next` каже дію, `check` каже проблему. Там скіл був би
переказом того, що інструмент і так друкує.

Отже: один змістовний скіл — планування, і два тонкі — робота та ревʼю перед PR.

| Інструмент | Куди кладеться |
|---|---|
| Claude Code | `.claude/skills/<name>/SKILL.md` |
| Cursor | `.cursor/rules/<name>.mdc` |
| Codex і решта | `AGENTS.md`, десять рядків із посиланням сюди |

**Ці файли породжуються з цієї методики командою `keel skills`, а не ведуться
руками.** Три тексти, які пишуть окремо, розходяться за місяць — це вже було зі
старою методикою. Перевірка ловить, якщо породжене правили вручну.

## Що робити далі

1. **`keel check`** — шість перевірок. Перше, бо без нього все інше на слові.
2. **`keel new` і `keel plan`** — без них крок нема з чого почати.
3. **`keel next`** — те, що замінює сторінку з етапами.
4. **`keel rev`** — без неї механізм редакцій мертвий: людині нема звідки взяти хеш.
5. **Хуки** `pre-commit` і `pre-push`, той самий бінарник, і CI за ними.
6. **`keel skills`** і породжені файли для Claude, Cursor та `AGENTS.md`.
7. **`keel/QUALITY.md`** — звірити вступ із Keel (див. відкрите).

Перші чотири — один інструмент, і робляться разом.

**Перший проєкт — `keel-agent`**, агент для локальних моделей на Elixir, у теці
поруч. Чистий аркуш: нічого не конвертується, і видно чесну вартість методики з
нуля. atomic-dev лишається на старій методиці; life_framework має майже 1400
рядків правил і фічі в старому форматі, тож конвертація там була б окремою
роботою до того, як ядро взагалі перевірене.

## Відкрите

- **Формат пакета `keel next`** — що саме в ньому й у якому вигляді: текст для
  моделі, JSON для скриптів, чи обидва.
- **Формат `.cursor/rules`** — треба звірити з тим, що Cursor читає сьогодні,
  перш ніж `keel skills` почне це породжувати.
