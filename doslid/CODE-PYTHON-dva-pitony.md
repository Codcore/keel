# У режимі `code-python` два різні Python, і плутати їх дорого

**Знайдено:** 23 серпня 2026, прогоном

## Що сталося

Модель написала `shopping_list.py`, а потім спробувала його перевірити:

    import shopping_list
    → ImportError: no module named 'shopping_list'. Available modules: os, abc, …

Чотири рази поспіль. Файл лежить на диску, а програма його не бачить.

## Чому

Їх справді два, і вони не той самий:

| | **програма моделі** | **проєкт** |
|---|---|---|
| чим виконується | Pyex, у нашому процесі | справжній `python3`, окремим процесом |
| що бачить | сорок неповних модулів, `tool` | всю стандартну бібліотеку |
| файли проєкту | **не імпортує** | імпортує звичайно |
| як дістатись | пише сама модель | `tool.run("python3", …)` |

Перевірено обома боками:

    import mine                                        → ImportError
    tool.run("python3", ["-c", "import mine; …"])       → працює

## Чому це не вада, а будова

Так само влаштований і `code-lua`: модель пише Lua, щоб **розпоряджатись**, а
програму проєкту запускає через `tool.run`. Різниця лише в тому, що там дві мови
різні й сплутати їх неможливо, а тут обидві — Python, і плутанина дармова.

Тобто ця межа — ціна тієї самої зручності, заради якої режим і заводився.

## Лік

Сказати прямо в промті, бо це **незнання, а не звичка** — а незнання промт
лікує:

    Your program cannot import the project's own files: `import shopping_list`
    will not find a shopping_list.py you just wrote. Run it instead — that is a
    real Python, with the whole standard library and the project on its path:

        out = tool.run("python3", ["-m", "pytest", "-q"])

**Побічний зиск:** через `tool.run` моделі доступна **повна** стандартна
бібліотека — `subprocess`, `tempfile`, `unittest.mock`, усе. Неповнота Pyex
стосується лише програми-розпорядника, а не коду, який модель пише людині.
