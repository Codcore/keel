# Код усередині Lua-рядка: подвійне екранування ламає продукт

**Спіймано:** 22 серпня 2026, випробування `0002-shopping`, gemma-4-26B.
**Ціна:** модель втратила щонайменше чотири ходи на пошук вади не там.

## Що сталося

Гемма писала програму на Python, кладучи її текст у Lua-рядок `[[...]]`:

```lua
local py_code = [[
def write_lines(lines):
    with open(FILE, "w") as f:
        for line in lines:
            f.write(line + "\\n")      -- ← ось воно
]]
tool.write("shopping.py", py_code)
```

Вона взяла перенос рядка як `\\n`, ніби Lua його розгорне. Але **`[[...]]` в Lua
екранування не обробляє зовсім** — рядок іде дослівно. Тож у файл `shopping.py`
потрапило `f.write(line + "\\n")`, а це в Python означає літеральні два символи:
зворотна похила й `n`.

Наслідок — усі покупки лягли **одним рядком**:

```
[ ] Milk\n\n[ ] Eggs\n
```

Далі все сходиться само: `remove 1` видаляє єдиний рядок, файл порожніє,
`list` каже «порожньо», тест падає.

## Чому модель цього не побачила

Її власний налагоджувальний вивід показував ваду прямо:

```
DEBUG PRE-REMOVE: 1. [ ] Milk\n\n[ ] Eggs\n
```

Один пункт із літеральними `\n` усередині. Але гемма шукала в іншому місці:

> the issue is likely that the `shopping_list.txt` file is not being cleaned up
> properly between tests or the file operations are behaving unexpectedly in
> this environment

Тобто підозрювала середовище, а не власне екранування. Три ходи поспіль вона
переписувала то програму, то тест, щоразу з тією самою вадою всередині.

## Чому це варте нашої уваги

Вада не в моделі й не в Python. Її **створює будова пісочниці**: щоб покласти
файл на диск, модель мусить укласти чужий код у Lua-рядок, тобто пройти два
шари екранування поспіль. Кожен такий шар — це нагода помилитись, і помилка
виходить мовчазна: файл записується, програма запускається, ламається щось
третє за три кроки звідти.

## Чого це НЕ означає

Що `tool.write` треба міняти. Він робить рівно те, що просять, і `[[...]]` в
Lua поводиться так, як написано в його ж підручнику.

## Що з цим можна зробити

Три шляхи, жоден не обраний:

1. **сказати про це в промті** — рядок на кшталт «`[[...]]` не розгортає
   екранування: пишіть перенос як справжній перенос, а не як `\\n`»;
2. **дати інструмент, що не потребує вкладання** — щось на кшталт
   `tool.write_lines(path, {рядок, рядок, …})`;
3. **лишити як є** — і рахувати це частиною випробування: модель, яка не
   плутається в двох шарах екранування, справді краща.

Третє має свою рацію: пастка чесна й однакова для всіх. Але вона міряє не те,
що ми хотіли міряти, і про це варто знати, читаючи результати.
