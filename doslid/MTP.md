# MTP і повільні заміри: дві хибні гіпотези й справжня причина

**Розслідувано:** 22 серпня 2026, спроба прогнати Qwen3.8-27B із чернеткою.

## Справжня причина

**Ноутбук працював на майже порожній батареї в режимі економії.** macOS у ньому
душить GPU, і це б'є по всьому одразу — префілу, декодуванню, будь-яких
обчисленнях.

Вимір, що це довів, — чисте множення матриць повз модель і сервер:

```
20 множень 4096x4096: 6.64 с  →  0.4 TFLOPS
```

Для порівняння: справний M-чип дає десятки TFLOPS. Тобто задушений був
**сам прискорювач**, а не якась із наших налаштувань.

Після перезапуску з підключеним живленням: `lowpowermode 0`,
`Now drawing from 'AC Power'`.

## Дві гіпотези, що виявились хибними

**Хибна гіпотеза 1: «MTP гальмує».** Я дістав 1.0 т/с із чернеткою й записав
це як ваду MTP. Спростувалось відразу: та сама конфігурація **без** чернетки
дала ті самі 1.0 т/с.

**Хибна гіпотеза 2: «сервер не той».** Я взяв
`mlx-vlm-patches/patches/mlxsrv.py` замість правильного
`llm-research/app/mlxsrv_lenient.py`. Сервер справді був не той (див. нижче),
але на швидкість це майже не вплинуло: правильний дав 1.6 т/с проти 1.0 —
однаково вдесятеро менше за очікувані 17.

**Урок:** перш ніж пояснювати повільність налаштуваннями, зміряй залізо.
Одне множення матриць за десять секунд відкинуло б обидві гіпотези відразу.

## Побічна знахідка: MTP потребує окремого сервера

Хоч вона й не пояснила повільність, вона правдива й важлива.

**Спекулятивне декодування реалізовано лише в `mlx_vlm`.** Наш працівник
(`priv/worker/worker.py`) стоїть на `mlx_lm`, який чернетки не приймає
взагалі. Тобто MTP недосяжний для `KeelAgent.Model.MLX` **за побудовою**.

`llm-research/app/mlxsrv_lenient.py` існує саме для цього. З його заголовка:

> `mlx_vlm.server`, який приймає моделі без зорових ваг. Навіщо: MTP
> реалізовано лише в `mlx_vlm`, а він падає на TextOnly-моделях із
> «Missing 393 parameters: vision_tower…». Але сама бібліотека вміє вантажити
> нестрого — `load(..., strict=False)`, — просто сервер цього не виставляє.

Плюс два патчі, без яких MTP не живе з нашими налаштуваннями:

| патч | нащо |
|---|---|
| `qwen35_qkv_patch` | без нього MTP + `--kv-bits` + `APC_ENABLED=1` дає `'tuple' object has no attribute 'shape'` |
| обрізання квантованого пакетного KV | без нього відкат після перевірки чернетки неможливий |

Ціна нестрогого завантаження названа там же: зорові шари лишаються
неініціалізованими. Для тексту безпечно; надсилати такій моделі зображення
не можна.

### Правильний запуск

```bash
APC_ENABLED=1 ./mlxenv/bin/python app/mlxsrv_lenient.py \
  --host 127.0.0.1 --port 8911 \
  --model lukaskremla/Qwen3.8-27B-4bit-MLX-TextOnly \
  --max-kv-size 32768 --kv-bits 8 --kv-group-size 64 \
  --draft-model mlx-community/Qwen3.8-27B-MTP-4bit \
  --draft-kind mtp --draft-block-size 4
```

Мітка `vlm` у їхній таблиці моделей означає **саме цей** сервер.

## Правило для всіх подальших замірів швидкості

Перед прогоном перевіряти:

1. **живлення** — `pmset -g ps` має казати `AC Power`, `pmset -g | grep
   lowpowermode` має давати `0`;
2. **заряд** — на низькому macOS душить GPU навіть у мережі;
3. **залізо** — множення матриць має дати десятки TFLOPS, не одиниці;
4. **спокій машини** — `uptime` з навантаженням у десятки означає, що міряти
   ще рано (після перезапуску Spotlight переіндексовує годинами).

`llm-research` до того ж клав **120 секунд охолодження** між прогонами, бо
похибка через тепловий стан доходила 8 %.

## Чи зачеплені попередні заміри

**Не зачеплені.** Усі сім записаних прогонів лежать у вузькій смузі:

| час | модель | швидкість |
|---|---|---:|
| 15:55 | gemma-4-26b | 35.6 т/с |
| 15:59 | laguna-xs-2.1 | 33.9 т/с |
| 16:04 | laguna-xs-2.1 | 40.5 т/с |
| 16:07 | mellum2-12b | 52.3 т/с |
| 16:26 | glm-4.7-flash | 30.5 т/с |
| 16:31 | qwen3.6 (think) | 34.9 т/с |
| 16:39 | qwen3.6 (nothink) | 35.0 т/с |
| **18:52** | **qwen3.8** | **1.0 т/с** |

Просідання від прогону до прогону немає — числа не повзуть вниз, а тримаються.
Обвал стався в двогодинній перерві між 16:39 і 18:52, коли ноутбук лишався
ввімкненим без живлення.

Зіпсований лише прогін Qwen3.8. Решту переміряти не треба.

**Але надалі стан машини має потрапляти в `metrics.json`** — інакше наступного
разу доведеться знову вгадувати заднім числом.

## Ornith + MTP не влазить у 36 ГБ

**Зміряно:** 22 серпня 2026, `pyros-vault/Ornith-1.5-35B-A3B-oQ4e-fixed-mtp`.

Ваги Ornith **уже містять 42 шари MTP** (`language_model.mtp.*`), тобто модель
сама собі чернетка. Але задіяти їх без другої копії не вийшло:

| як запускали | що вийшло |
|---|---|
| без `--draft-model` | сервер живий, **MTP не вмикається** — у логу про чернетку нічого |
| `--draft-model` = ті самі ваги | `Drafter ready`, потім **смерть на першій генерації** |

Замір смерті — своп росте, процес зникає:

```
завантажено. RSS 2.1 ГБ, swap 16011 МБ
 [9с] swap 17408 МБ
[15с] СЕРВЕР ПОМЕР
```

**Арифметика:** ваги 20 ГБ + друга копія для чернетки 20 ГБ = 40 ГБ на машині
з 36 ГБ. Плюс KV-кеш під час генерації. Тому сервер переживає завантаження й
гине саме на генерації.

Опції «взяти чернетку з уже завантаженої моделі» в `mlxsrv_lenient` немає —
перевірено через `--help`: є лише `--draft-model`, `--draft-kind`,
`--draft-block-size`.

**Висновок:** на цій машині MTP доступний тільки там, де чернетка — окремі
малі ваги (як `Qwen3.8-27B-MTP-4bit` при 14-гігабайтній основній моделі).
Моделі з вбудованим MTP потребують або більшої пам'яті, або підтримки
спільного завантаження в сервері.


## Чернетку забули ввімкнути в запускачі — і не помітили б

**Спіймано:** 23 серпня 2026, оператором, за одним числом у звіті.

`tools/sweep.sh` піднімав сервер однаково для всіх ваг:

```
--model … --max-kv-size 65536 --kv-bits 8 --kv-group-size 64
```

Без `--draft-model`. Тобто голова MTP на 253 МБ, яка в нас лежить готова для
Qwen3.8, не задіювалась узагалі.

**Ціна, зміряна на тому самому завданні:**

| | без чернетки | з чернеткою |
|---|---:|---:|
| декодування | 8 т/с | **19.7 т/с** |
| перший хід | 2755 токенів за 330 с | 1883 за 107 с |

Тобто вдвічі з половиною повільніше — і кожна помилка моделі коштувала близько
шести хвилин замість двох.

**Як помітили:** оператор спитав «а вона без MTP чи що? вона має давати 17
токенів». Тобто ваду знайшло **очікування, звірене з числом**, а не заслон і
не тест. У звіті швидкість була, але сама собою вона нічого не кричала.

**Що з цього варте правила:** у звіті прогону має стояти не лише швидкість, а
й **чи ввімкнена чернетка**. Інакше повільний прогін виглядає властивістю
моделі, а не нашим недоглядом.

Полагоджено: `sweep.sh` вмикає чернетку там, де вона є окремими вагами. У
Ornith та iQ-кванта MTP вбудований у самі ваги, і задіяти його не вдалося —
див. вище.
