# `native` і `code-python`: рівні по інструментах, різні по виразності

**Перевірено:** 23 серпня 2026, перед випробуванням на Elixir

## Вісім дій, дві мови, однакова відповідь

Кожна дія прогнана в обох режимах на свіжій теці; порівнювалось **те, що бачить
модель**, а не внутрішні терми.

| дія | у Lua | у Python |
|---|---|---|
| `list` | `lib/` | `lib/` |
| `read` | вміст файлу | те саме |
| `write` | `created: …/b.txt` | те саме |
| `edit` | `changed: …/lib/a.ex` | те саме |
| `grep` | `lib/a.ex:1: defmodule A do` | те саме |
| `glob` | `lib/a.ex` | те саме |
| `run` | `output: 7 ⏎ status: 0` | те саме |
| відмова | `nil ⏎ file is missing or unreachable` | те саме |

**Жодної розбіжності.**

## Але виразність різна, і це не вада

| | `native` | `code-python` |
|---|---|---|
| ті самі сім інструментів | так | так |
| кілька дій за хід | так, по черзі | так |
| **розгалуження за результатом** | **ні** | **так** |
| цикл по списку файлів | ні | так |
| проміжні змінні | ні | так |

У `native` модель шле виклики **наосліп**: складаючи другий, вона не знає
результату першого. У `code-python` вона пише `if`, `for`, змінну — і робить за
один хід те, на що інакше пішло б три.

## Вада, знайдена цією ж перевіркою

`Program.show/1` чекав від списку **пари** `{ключ, значення}`, бо так приходять
таблиці Lua. Python-режим віддає звичайний перелік рядків — і показ **падав
виїмком**, тобто хід гинув на `tool.list`, `tool.grep`, `tool.glob`.

Не бачили ми цього тому, що моделі здебільшого **друкували** результат, а не
вертали: надруковане йде іншим шляхом. Знайшлось аж на порівнянні режимів між
собою — тобто там, де ми вперше поставили їх поруч на однакових даних.

**Ще один доказ, що два режими корисні як дві перевірки того самого коду.**
