# Pyex: перевірено руками, придатний

**Коли:** 23 серпня 2026
**Що це:** інтерпретатор Python 3 на Elixir, `{:pyex, "~> 0.1"}`,
`github.com/ivarvong/pyex`. Єдина версія 0.1.0 від 14 квітня 2026, 116
завантажень усього.

## Збірка: не з першого разу

На Elixir 1.20.3 не компілюється: нова перевірка типів робить **помилками** те,
що раніше було попередженнями про необовʼязкові залежності.

Треба доставити три, яких Pyex сам не тягне:

    {:postgrex, "~> 0.20"}   # Postgrex.Error у lib/pyex/stdlib/sql.ex
    {:decimal, "~> 2.0"}     # Decimal у тому ж файлі
    {:explorer, "~> 0.11"}   # Explorer.Series/DataFrame у methods.ex

Після цього збирається чисто. **Ціна названа:** `explorer` тягне Rust-NIF, тобто
важку збірку, і все це заради pandas та SQL, яких нам не треба зовсім.

## Виклик наших функцій: працює

Форма — модуль із кортежами `{:builtin, fn}`, і модель його **імпортує**:

```elixir
Pyex.run(code, modules: %{"tool" => %{
  "write" => {:builtin, fn [path, text] -> … end},
  "read"  => {:builtin, fn [path] -> … end}
}})
```

```python
import tool
a = tool.write("shopping.py", "print('hi')")
b = tool.read("shopping.py")
```

Повернулось: `["created: shopping.py (11 байт)", "вміст shopping.py", …]`

**Дрібниця, яку треба знати:** список Python приходить у власній формі —
`{:py_list, ["-q"], 1}`, — тож аргументи для `tool.run` доведеться розгортати.

## Межі: тримає всі, що нам потрібні

Перевірено кожну окремо:

| спроба | наслідок |
|---|---|
| `open("/etc/passwd")` | відмова (`io`) |
| `import os` | відмова |
| `import subprocess` | відмова (`import`) |
| `__import__('os').getcwd()` | відмова |
| нескінченний цикл | відмова за часом (`timeout`) |
| глибока рекурсія | відмова |
| наш `tool.ping()` | **працює** |

Тобто «deny-by-default» із їхнього опису — не обіцянка, а те, що видно руками.

## Договір: що саме вертається

Перевірено кожен випадок окремо.

**`{:ok, значення, ctx}`**, де `значення` — це **останній вираз**, як у REPL:

| код | значення |
|---|---|
| `1 + 1` | `2` |
| `x = 5` | `5` |
| `y = tool.ping()` | `"pong"` |
| `print("привіт")` | `nil` (це те, що вертає сам `print`) |

**`return` не потрібен** — і це помітно краще за Lua, де його відсутність коштувала
нам окремої вади: модель писала `tool.read(...)` без `return`, діставала порожньо
й ішла по колу (`BUG-porozhniy-perelik.md`).

**Надруковане живе в `ctx.output_buffer`** — переліком, **зворотним порядком**:

    print('один'); print('два')  →  ["два\n", "один\n"]

Поруч `ctx.output_bytes` — скільки надруковано. Кирилиця приходить байтами, які
треба зібрати в рядок.

## Дві пастки, спіймані пробою до внесення в агента

### 1. Перелік приходить розверненим

    ["a", "b", "c"]  →  {:py_list, ["c", "b", "a"], 3}
    [1, 2, 3]        →  {:py_list, [3, 2, 1], 3}

Без розвороту кожен `tool.run` **мовчки перекручував би команду**:
`pytest -q file.py` став би `file.py -q pytest`. Помилки не було б — була б
незрозуміла поведінка.

Так само розвернутий і `output_buffer`.

### 2. Рядки приходять закодованими двічі — і лікується це **на вході**

    print("кирилиця тут")  →  "ÐºÐ¸ÑÐ¸Ð»Ð¸ÑÑ ÑÑÑ"

Це UTF-8, закодований ще раз. Розкручується зворотним перетворенням:

```elixir
:unicode.characters_to_binary(said, :utf8, :latin1)   # → "кирилиця тут"
```

ASCII від цього не страждає.

**Але розкрутити на виході — замало.** Pyex кодує двічі **свої** літерали, а те,
що приходить від нас, лишає як є. Доки рядок один — видно й лікується. Але
`print` склеює:

```python
text, err = tool.read("немає.py")
print("відмова:", err)          # літерал двічі + наш рядок один раз
```

Виходить половина двічі, половина раз — **суміш, яку розкрутити неможливо**:
обидві половини правильні, а разом вони не є нічим.

Перевірено окремою пробою: той самий рядок, відданий «як є», не розкручується;
відданий закодованим — читається бездоганно.

**Отже правило: усе, що ми віддаємо в Pyex, кодуємо так само, як він кодує свої
літерали.** Тоді всередині все однакове, і одне розкручування на виході лікує
весь рядок.

І дзеркально: значення, що вертається **не через `print`**, теж треба
розкрутити — воно пройшло крізь кодування на вході й не проходило крізь
`output_buffer` на виході. Без цього `tool.run` віддавав би правильний стан і
нечитний вивід.

**Обидві спіймані до внесення в агента** — саме тому проба й робилась на
підробних інструментах в окремому проєкті.

## Договір відмови — той самий, що в Lua

```python
text, err = tool.read("nope.py")
if text is None:
    print("відмова спіймана:", err)
```

    » відмова спіймана: file is missing or unreachable
    » успіх без пари: created: a.py

Тобто наш `[nil, reason]` розпаковується парою, а успіх приходить одним
значенням — модель пише звичайний Python і не мусить нічого запам'ятовувати.

## Межі виводу й пам'яті

| спроба | наслідок |
|---|---|
| друк десяти мегабайтів | відмова (`limit`) |
| рядок на 50 мільйонів символів | відмова |
| звичайний друк | працює |

## Перевірено повністю

Інструменти, відмови, кодування, порядок аргументів, час, вивід, пам'ять — усе
руками, кожне окремо. Жодне число тут не з опису проєкту.

## Модулі є, але неповні — і це не видно з переліку

`ImportError` перелічує сорок із гаком модулів. Але наявність модуля не означає
наявності того, що в ньому має бути.

Перевірено викликами, а не переліком:

| виклик | наслідок |
|---|---|
| `json.dumps({"a": 1})` | працює |
| `re.sub("a", "b", "aaa")` | працює |
| `math.sqrt(9)` | працює |
| `os.path.join("a", "b")` | працює |
| `pathlib.Path("a") / "b"` | працює |
| `datetime.datetime.now()` | працює |
| `sys.argv` | працює |
| **`os.getcwd()`** | **AttributeError** |
| **`unittest.TestCase`** | **AttributeError** |

Тобто `os` у переліку є, а `os.getcwd` — немає; `unittest` є, а `TestCase` в
ньому немає.

**Чим це коштувало:** Mellum2-12B двічі поспіль писала `os.getcwd()`, читала
помилку, «розуміла проблему» — і писала знову.

**Що з цього в промті:** не перелічувати те, що зміниться з версією
бібліотеки, а сказати правило — «модуль може бути неповним; не плануй навколо
того, чого ще не пробував у цьому проєкті: поклич раз і подивись».

## Висновок

**Придатний.** Моделі дістається Python — мова, якою вони й так пишуть, — а
заслони лишаються наші.

**Чого це не вирішує** (і це названо ще до проби): вкладення мови в мову. Писати
Elixir усередині рядка Python зламається на його ж `\"\"\"` так само, як Python
ламався в Lua `[[ ]]`. Для Python-проєктів `code-python` природний; для чужих
мов — ні.

**Що зважити перед внесенням у стенд:** версія 0.1.0, один автор, і три зайві
залежності з важким Rust. Для клона-стенда це прийнятно; у `keel` — ні.
