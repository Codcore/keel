# `max_tokens` не йшов на дріт — довгий вивід обрізало посеред коду

**Знайдено:** 22 серпня 2026, під час розслідування зривів GLM.
**Полагоджено:** там-таки, правкою прогону в `config/config.exs`.

## Що було

`KeelAgent.Model.OpenAICompatible` бере з опцій `:max_tokens` і кладе на дріт —
але в конфігу його **ніхто не задавав**. Тіло запиту, зняте посередником:

```json
{
  "stream": true,
  "model": "mlx-community/GLM-4.7-Flash-4bit",
  "temperature": 0.6, "top_k": 40, "top_p": 0.95,
  "stream_options": {"include_usage": true}
}
```

Ані рядка про стелю. Сервер `mlxsrv` підставляв свою усталену — **2048
токенів**.

## Чому це важить

На випробуванні з одним файлом тестів 2048 вистачало, і вада не бачилась. Але
кожен зіпсований хід GLM мав рівно `вихід 2048` — тобто впирався в стелю, а не
спинявся сам:

```
хід 1: вхід 775 токенів, вихід 2048
хід 2: вхід 2853 токенів, вихід 2048
хід 3: вхід 4931 токенів, вихід 2048
```

На проєкті — де модель пише кілька файлів із тестами за один хід — 2048
обрізає відповідь **посеред коду**. Модель не встигає дописати ані файл, ані
закритий Lua-блок, і хід згоряє на синтаксичній помилці, яку вона не робила.

**Ознака в журналі:** `finish_reason: length` замість `stop`.

## Лік

```elixir
config :keel_agent, KeelAgent.Session,
  ...
  max_tokens: 16384,
```

Перевірено на дроті посередником:

```json
{"stream": true, "temperature": 0.2, "top_k": 40, "top_p": 0.95,
 "max_tokens": 16384, "stream_options": {"include_usage": true}}
```

## Що з цього належить агентові, а не досліду

Зараз стеля живе в **правці прогону** — тобто в нашому клоні, не в проєкті.
У самому `keel-agent` усталеного значення немає, і будь-хто, хто підніме
агента без цього рядка, дістане чужі 2048.

Варте окремого рішення: чи ставити усталене в самому агенті, і яке. Міркування
за 16384: цього досить на кілька файлів із тестами за хід, і водночас це стеля,
що ловить зрив у нескінченний повтор раніше, ніж він з'їсть увесь контекст.
