# Native tool calling проти fenced code block: ми читаємо лише друге

**Спіймано:** 22 серпня 2026, побічно, під час перевірки заголовка журналу.

## Що сталося

Проста розмова, гемма-4-26B, промт «say hi». Модель дістала наше нагадування
про доказ і відповіла так:

```
<|tool_call>call:lua:```lua
return tool.list(".")
```<tool_call|>
```

Блок із міткою `lua` **є**, він правильний, і всередині робочий код. Але він
загорнутий у `<|tool_call>` … `<tool_call|>` — власні службові токени гемми,
якими її навчали позначати виклик інструмента.

Наш parser шукає fenced code block і цієї обгортки не чекає. Тому:

```
[програма] You answered without a single tool call — so without evidence.
[програма] You answered without a single tool call — so without evidence.
[не сталося] {:unchecked, 2}
[кінець] failed: {:unchecked, 2}
```

Двічі нагадали, тоді записали відмову — за виклик, який модель зробила.

## Чому це важить

Заслон доказу спрацював **проти правди**: модель зробила рівно те, що просили,
а ми записали, що вона не зробила нічого. У випробуванні це рахується як
провал моделі, хоч провал наш.

І трапляється це не завжди: у справжньому прогоні `0002-shopping` гемма писала
блоки чисто, без обгортки. Тобто вада мовчазна й нерівна — вилазить тоді, коли
модель вирішує, що це «виклик інструмента», а не просто код.

## Чому вона взагалі так робить

`<|tool_call>` — службовий токен із її власного шаблону розмови. Ми не
надсилаємо жодного опису інструментів у форматі, який гемма знає (`tools` в
запиті), тож вона мусить здогадуватись, і частину часу здогадується своїм
рідним способом.

## Що з цим можна зробити

1. **чистити обгортку перед добуванням** — знімати `<|...|>` довкола блоку;
   дешево й лагодить саме цей випадок;
2. **приймати виклик у рідному форматі моделі** — тобто вміти читати
   `tool_calls` з відповіді, а не лише загороджені блоки; це велика робота;
3. **сказати в промті прямо** — «не загортай блок ні в що».

**Не полагоджено.** Перше виглядає найдешевшим, але воно про добування блоку —
серце циклу, — і робити це поспіхом посеред прогону не варто.


## Laguna робить те саме — і гірше

22 серпня, випробування `0002-shopping`, перший хід Laguna-XS-2.1:

```
I'll build this shopping list CLI tool for you. Let me start by exploring
the project structure to understand what's already there.<tool_call>tool.list('.')
```

Тут навіть **немає fenced code block** — самий службовий токен `<tool_call>` і
виклик за ним. Гемма хоч клала блок усередину обгортки; Laguna обходиться без
нього зовсім.

**Двоє з восьми.** Це вже не примха однієї моделі.

## Чому це стається

Ми шлемо запит **без поля `tools`** — тобто не оголошуємо інструменти в
форматі, який ці моделі знають із навчання. Ми описуємо їх словами в system
prompt і чекаємо на fenced code block у відповідь.

Моделі, навчені на native tool calling, частину часу відповідають своїм рідним
способом: службовими токенами, які в OpenAI-сумісному API мали б приїхати
окремим полем `tool_calls`, а не в тексті. Наш parser бачить лише текст і
блоку в ньому не знаходить.

## Три шляхи, тепер із оцінкою

1. **чистити службові токени перед розбором** — знімати `<tool_call>` і подібні
   обгортки, тоді шукати блок. Дешево, лагодить гемму. Laguna цим не
   лікується: у неї блоку немає взагалі;
2. **читати `tool_calls` з відповіді** — тобто підтримати native tool calling
   як другий шлях поруч із блоком. Велика робота, але лагодить обидві;
3. **сказати в system prompt прямо** — «не використовуй службових токенів
   виклику, лише блок». Найдешевше, але покладається на слухняність моделі.


## Це ціла родина, а не окремі ваги

Прогін `0002-shopping` 22 серпня, після того як parser навчився впізнавати
службові токени й чесно казати, що робити:

| ваги | як кличе інструмент | наслідок |
|---|---|---|
| gemma-4-26B | `<\|tool_call>call:lua:` + блок усередині | **лік допоміг** — блок став видимим, завдання виконано |
| Laguna-XS-2.1 | `<tool_call>tool.list('.')`, без блоку | перейшла на блок, але загрузла інде |
| Ornith-1.5-35B | XML: `<tool_call><function=例><parameter …>` | не перебудувалась, 40 ходів |
| Qwen3.8-27B | XML: `<tool_call><function=tool><parameter=list>` | те саме, 40 ходів |

Ornith і Qwen3.8 — обидві родом із Qwen, і розмітка в них однакова. Тобто це
не примха окремих ваг, а **навчений формат цілої родини**.

## Що з цього випливає

Чищення обгортки рятує лише гемму — там блок справді є. Для Qwen-родини блоку
немає **зовсім**: виклик виражений самою XML-структурою, і прочитати його
можна лише розібравши цю структуру.

Тобто вибір звужується до двох:

1. **навчитись читати `tool_calls`** — тобто оголошувати інструменти полем
   `tools` у запиті й брати виклик із відповіді, як робить OpenAI-сумісний API.
   Це велика робота, але вона знімає ваду для всіх;
2. **лишити як є** — і рахувати нездатність перейти на наш формат частиною
   випробування. Чесно, але тоді дві з восьми моделей оцінюються не за вміння
   програмувати, а за слухняність до чужої розмітки.

Наша чесна відповідь «ти кликав своїми токенами, поклади код у блок» **не
допомогла жодній із Qwen-родини**: обидві повторювали своє до кінця ходів.


## Знаряддя для ліку в нас уже є: `ReqLLM` уміє `:tools`

Знайдено 23 серпня 2026, побічно — з повідомлення про помилку, коли ми
спробували послати `:repetition_penalty`:

```
unknown options [:repetition_penalty], valid options are:
[:temperature, :max_tokens, :base_url, :top_p, :top_k,
 :frequency_penalty, :presence_penalty, :seed, :stop, :user,
 :system_prompt, :tools, :tool_choice, :output, :provider_options, …]
```

**`:tools` і `:tool_choice`** — тобто наша ж бібліотека вміє оголошувати
інструменти так, як це робить OpenAI-сумісний API, і читати виклик із поля
`tool_calls` у відповіді.

Ми цим не користуємось. Інструменти описані **словами** в system prompt, а
виклик очікується **текстом** — fenced code block із міткою `lua`.

## Чому це міняє вибір ліку

Раніше вибір стояв так:

1. чистити службові токени перед розбором — рятує лише гемму;
2. навчитись читати `tool_calls` — «велика робота»;
3. просити в промті не використовувати службових токенів — покладається на
   слухняність, і Qwen-родина її не виявила.

Тепер видно, що друге — **не така вже й велика робота**: транспорт її вже
підтримує. Треба:

- описати наші сім інструментів як JSON Schema й передати в `:tools`;
- навчитись брати виклик із `tool_calls`, а не лише з тексту;
- лишити fenced code block як другий шлях — ним ходять гемма й Qwen3.6, і
  ламати те, що працює, не варто.

## Чого це НЕ вирішує

**Lua лишається.** Наші інструменти — це не окремі функції, а **програма на
Lua**, яка їх кличе: одним ходом модель робить кілька дій, перевіряє
результати, розгалужується. `tools` OpenAI так не вміє — там один виклик з
іменем і аргументами.

Тобто перехід на native tool calling означав би або віддати Lua-цикл (велика
втрата: саме він дає моделі робити багато за хід), або оголосити **один
інструмент** `run_lua(code)` і брати його аргумент.

Друге виглядає розумним: розмітка стає рідною для моделі, а зміст лишається
наш. Але це вже зміна задуму, не латка, і рішення тут ваше.


## Ornith: перехід на блоки був випадковим, не набутим

22 серпня, після виправлення `top_p` з 0.95 на 1.0, Ornith один раз написала
чистий блок:

```lua
return tool.list('.')
```

Я записав це як «правильні параметри прибрали блукання чужою розміткою». **Це
було передчасно.**

23 серпня, ті самі параметри, промт шостої редакції:

```
  41×  <tool_call>
```

Сорок один хід із сорока одного — рідною XML-розміткою. Пісочниця порожня.

**Отже перехід на блоки був винятком, а не набутою поведінкою.** Ornith кличе
інструменти своїм способом стабільно, і ані параметри, ані промт цього не
міняють.

Це підтверджує висновок вище: для Qwen-родини єдиний шлях — навчитись читати
`tool_calls`. Усе інше — сподівання, що модель поводитиметься не так, як її
вчили.


## Ornith: ми випробовуємо її в режимі, для якого вона не зроблена

Картка моделі (`ornith-ai/Ornith-1.5-35B-A3B`) позиціонує її **саме як
агентську для коду** й наводить числа проти прямого суперника:

| випробування | Ornith | Qwen3.6-35B |
|---|---:|---:|
| SWE-bench Verified | 79 % | 73.4 % |
| **Terminal-Bench 2.1** | **67.8 %** | 52.5 % |
| DeepSWE | 22 % | 0 % |

Тобто на агентських бенчмарках вона має бути **кращою** за Qwen3.6.

**У нас 23 серпня:** Ornith — 41 хід, усі в `<tool_call>`, пісочниця порожня.
Qwen3.6 — два ходи, дванадцять тестів, повна документація.

Причина названа в тій самій картці: модель оптимізована під **tool-calling
через OpenAI-сумісний API**. Ми вимагаємо від неї текстову розмітку, якої вона
не вчила, і не приймаємо ту, яку вчила.

**Тобто ми міряємо не модель, а її здатність відмовитись від власного
навчання.**

## Друге, чого ми не врахували

Картка каже, що це **reasoning-модель**: «generating chain-of-thought traces
before answers». Ми ганяємо всіх із `thinking: false`.

Це окрема гіпотеза, і перевіряти її треба окремо — але вона теж може
пояснювати частину провалу.

## Чому це підсумковий доказ

Модель, що претендує на найкращу агентську роботу серед свого розміру, у нас
дає нуль. Не тому, що вона гірша, а тому, що наш цикл не говорить її мовою.

Поки `tool_calls` не підтримані, **числа Qwen-родини в цьому досліді не
означають нічого про самі моделі**.
