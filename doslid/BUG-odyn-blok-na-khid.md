# «Один блок на хід» відкидає роботу цілком, а не просить її поділити

**Спіймано:** 22 серпня 2026, `0002-shopping`, Devstral-24B.

## Що сталося

Людина попросила зробити командну програму зі списком покупок. Devstral за
**один хід** написала весь проєкт: програму, тести, файл даних і пояснення, як
цим користуватись. Вісімнадцять загороджених блоків.

У відповідь:

```
the turn has 18 programs, but only one runs — leave a single block
```

**І все.** Жоден із вісімнадцяти не виконався. Півтори тисячі вихідних токенів
і 158 секунд декодування пішли в нікуди.

Наступного ходу вона написала чотири блоки — знову відмова. Тобто читає й
скорочується, але кожна спроба коштує повного ходу.

## Чому правило потрібне

Це не примха. У `Session.Program`:

> **Один блок на хід.** Два — відмова: виконати перший означало б вибрати за
> модель, а обидва — склеїти дві програми з чужими змінними.

Обидві причини чинні. Виконати перший і промовчати про решту — це тихо
зробити не те, що модель просила. Склеїти всі — це змішати їхні `local`.

## Чому воно однаково вада

**Відмова не відповідає на питання, яке в моделі насправді є.** Модель не
помилилась синтаксисом — вона мислить **цілим проєктом**, а наш цикл мислить
**одним кроком**. Це не непорозуміння, а різниця в масштабі, і повідомлення її
не називає.

«leave a single block» читається як «викинь решту», а не як «зроби це за
кілька ходів». Devstral і скорочувалась — з вісімнадцяти до чотирьох, — замість
розбити роботу на послідовність.

## Три можливі ліки

1. **сказати повніше** — «пиши по одному блоку за хід; те, що не вмістилось,
   зробиш наступним ходом, вони йдуть один за одним». Найдешевше, нічого не
   ламає;
2. **виконати перший і сказати про решту** — «виконано перший блок із 18,
   решту не чіпано; шли їх по черзі». Хід не пропадає намарно, але ми
   вибираємо за модель;
3. **дозволити кілька блоків одним пакетом** — виконувати послідовно в спільній
   пісочниці, повертати результат кожного. Найбільша робота, і вона знімає
   причину, заради якої правило робилось.

**Не полагоджено.** Перше виглядає очевидним і дешевим, але це зміна
системного промту — тобто норма, і вона ваша.

## Ціна, названа числами

Devstral: два ходи поспіль відкинуто цілком, разом близько 2500 вихідних
токенів і понад три хвилини роботи. На моделі, що дає 9 т/с, це дорого.


## Глухий кут: модель лишає не ту половину

Тридцятий хід тієї самої Devstral. Вона пише файл і одразу перевіряє його —
двома блоками в одному ході:

```lua
return tool.write('mix.exs', 'defmodule M do use Mix.Project … end')
```
```lua
return tool.run('mix', {'compile'})
```

Хід відкинуто. Наступного ходу вона лишає **один блок — і це перевірка**:

```
[каже]     return tool.run('mix', {'compile'})
[програма] ** (Mix) Could not find a Mix.Project, please ensure you are
           running Mix in a directory with a mix.exs file
```

**Файл так і не створено.** Запис був у відкинутій половині.

Далі вона шукає причину не там, де та є:

> Let me check if there's a hidden character or encoding issue in the file
> The file appears to be created correctly

```lua
return tool.run('python3', {'-c', 'print(repr(open("mix.exs").read()))'})
```

Тобто перевіряє кодування файла, якого немає, — бо з відмови «leave a single
block» не видно, що **записаного не сталося**.

## Це вже не незручність, а пастка

«Створити й перевірити» — найприродніша пара дій, і модель робить її в один
хід. Наше правило розриває пару, а повідомлення не каже, **яку половину
лишити**. Devstral лишила перевірку — і застрягла назавжди: перевіряти нічого,
бо створення не сталося.

Ліки з переліку вище тепер видно чіткіше:

- **сказати повніше** мусить називати саме цей випадок: «перший блок виконано
  не буде — надішли його наступним ходом **першим**»;
- **виконати перший і сказати про решту** розв'язує пастку сам собою: запис
  стався б, і перевірка пішла б наступним ходом.

Друге виглядає тепер кращим за перше, хоч і коштує принципом «не вибирати за
модель».
